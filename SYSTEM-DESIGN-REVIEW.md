System Design Review — it-knowledge-base

Проект для своего размера выстроен грамотно. Архитектурные решения осознанные, без лишних слоёв. Ниже — что нашёл, по убыванию серьёзности.

---
Критично (может реально сломаться)

1. depends_on без condition: service_healthy в docker-compose

# сейчас:
depends_on:
  - qdrant          # ждёт только _запуска_ контейнера, не готовности

# должно быть:
depends_on:
  qdrant:
    condition: service_healthy

kb-api стартует сразу после появления процесса Qdrant, но Qdrant ещё не принимает соединения. Lifespan у FastAPI вызывает get_model() (20-30с), потом делает get_client() при первом запросе — к этому моменту Qdrant обычно уже жив, так что на практике везёт. Но это надежда, не гарантия. При медленном железе — краш при старте.

---
Высокий риск (технический долг с зубами)

2. qdrant/qdrant:latest — нет пина версии

Следующий docker compose pull может притащить новую major-версию с breaking changes в формате хранилища или API. Для личного проекта это «работало вчера, сегодня нет» без очевидной причины. Пинуй конкретную версию: qdrant/qdrant:v1.14.1.

3. Устаревший docstring в mcp_server.py (строка 27)

"""Семантический поиск по личной базе знаний (222 технические статьи:

README говорит 273 ссылки, каталог — 9 разделов. Claude Desktop читает этот docstring как описание инструмента — LLM получает неверную метаинформацию, что влияет на то, когда он решает вызвать инструмент.

---
Средний (tech debt, не горит)

4. KB_API продублирован в двух местах

- kb_core.py:24 — KB_API_URL = "http://127.0.0.1:8000"
- mcp_server.py:21 — KB_API = "http://127.0.0.1:8000"

Поменяешь порт — забудешь один из двух. Вынеси в переменную окружения (KB_API_URL) и читай из неё в обоих файлах.

5. LM_STUDIO_URL и KB_API_URL — hardcoded, не env-var

rag.py:22 — LM_STUDIO_URL = "http://localhost:1234/v1" без возможности переопределить. Если когда-то запустишь webui или rag не на той же машине — придётся лезть в код. os.environ.get("LM_STUDIO_URL", "http://localhost:1234/v1") — двух строк хватит.

6. Torch и зависимости без пинов версий

requirements.txt / requirements-api.txt — только >=. При pip install на новом окружении можешь получить несовместимые версии. Для производительного использования — pip freeze > requirements.lock.txt или минимум пины на major-minor (FlagEmbedding~=1.2).

---
Низкий (nice-to-have, не трогать пока работает)

7. Docker — root user в контейнере

Dockerfile не создаёт непривилегированного пользователя. Для localhost-личного инструмента — ок, но классика best practices — добавить USER appuser.

8. start_period: 120s в kb-api healthcheck

Модель грузится за 20-30с, образ собирается с прогретым кешем. 120s — перестраховка с запасом. В реальности можно опустить до 60s, быстрее детектишь проблемы при старте.

---
Что сделано правильно (чтоб не только ругаться)

- Архитектурное разделение — kb-api несёт тяжёлую модель, mcp_server.py — тонкий клиент без torch. MCP стартует мгновенно. Правильный выбор.
- Гибридный поиск (dense + sparse, RRF) для технического KB — именно то что нужно: термины ловит sparse, семантику — dense.
- Overfetch x3 с дедупликацией по URL — умное решение, один лучший чанк на статью вместо нескольких.
- uuid5(url#chunk_index) как ID — идемпотентная индексация, повторный запуск не дублирует данные.
- trust_env=False во всех httpx клиентах — обязательно при локальном прокси, сделано везде.
- Model baked in image + HF_HUB_OFFLINE=1 — правильно, не зависишь от HF Hub в runtime.
- stdout → stderr в MCP контексте — без этого JSON-RPC поток был бы засорён, сделано корректно.
- LangGraph с комментарием про будущие ноды — не преждевременная абстракция, а обоснованный задел.
- /health проверяет реальный Qdrant, не просто return ok — нормально.
